# 游戏任务登记与归档

任务定义服务已有可运行的本机开发实现；当前 Godot 客户端不依赖联网服务。玩法定义来源是 `data/quests/catalog.json`，每份存档的 `quest_journal` 保存任务实例。`server/quest_registry.py` 已将定义导入本地开发数据库 `server/var/quests.sqlite3` 的 `quest_types` 和 `quest_definitions` 两张表，可按类型、触发事件和完成处理器查询；尚未部署到远端服务端。`server/migrations/001_quest_registry.sql` 是 PostgreSQL 服务端建表迁移，尚未部署；不能把本地存档或本地开发库称为远端服务端落库。后续玩家任务状态联网时须绑定真实玩家标识，复用原子业务事务与幂等校验，不能维护另一份相互漂移的任务规则。

## 本地开发任务数据库

从项目根目录运行 `python server/quest_registry.py import` 建库并同步配置；运行 `python server/quest_registry.py list` 只读查询。支持 `--database` 和 `--catalog` 指定开发库和配置。修改任务仍需先确认类型、触发、完成条件，然后修改 JSON 并重新导入；不要手工修改数据库形成第二套规则。

上述命令要求Python 3。当前机器未将python加入PATH，已验证可用的PowerShell启动方式为：

```powershell
& 'C:/Users/KSG/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe' -X utf8 server/quest_registry.py serve
```

在项目根目录执行；将`serve`替换为`import`或`list`即可导入或查询。

导入前验证类型引用和条件结构，所有定义在同一事务中更新；重复导入不会重复记录，错误时回滚，不删除既有定义。数据库文件在 `server/.gitignore` 排除，可从配置重建。工具仅管理任务定义，不伪造玩家账户、探索到达或完成事件。运行 `python -m unittest discover -s server -p test_quest_registry.py -v` 验证持久化、幂等、外键、非法配置与事务中途失败回滚。

运行 `python server/quest_registry.py serve` 启动本机开发查询服务，默认监听 `127.0.0.1:8766`，Ctrl+C退出，端口可通过 `--port` 修改。`GET /quest-types` 查询类型及操作规则，`GET /quests` 查询任务定义，`GET /quests?type=exploration` 按类型筛选。接口直接只读查询实际数据库。验收已启动临时服务并发出真实HTTP请求，测试后已关闭；没有留后台进程，也没有对外网开放。远端部署、玩家账户及客户端联网不是当前任务定义登记功能的依赖。

## 存档与 UI 契约

`SaveManager.quest_snapshot()` 纯读返回 `{active: [], archived: []}`；每项含 `id`、`type`、`type_name`、`title`、`subtasks`、`status`、`unread` 与定义条件。`has_unread_quests()` 供入口红点使用。

新接入的活动任务 `unread = true`。只有玩家主动打开当前任务时调用 `mark_active_quests_read()`，自动展开教学、任务完成展开、重新进入场景均不能清除红点。已读接口返回 `{success, changed}`；失败时恢复原内存和文件，UI 不能假装成功消除红点。无变化不重复保存。

已完成任务从活动列表移入归档，`status = archived`、`unread = false`。归档单向、重复事件不重复接单、不复活归档任务，也不补发奖励。当前订单子任务的实时计数仍使用原经营数据；注册表仅定义名称与处理器，不保存另一份易失配的计数。

“当前任务”仅展示 `active` 中的进行中任务，不提供“进行中／已归档”页签或历史完成列表。归档只保存在本地任务日志中，供进度恢复与幂等判断使用。订单交付成功后立即移除该主任务及其子任务，不因完成动效重新展示；进行中的订单仍保留领取食材、制作料理子任务的完成动效。没有进行中任务时显示“暂无进行中的任务”。

探索任务与订单主任务共用金棕底色、深棕边框、标题字号及状态组件：标题前显示待完成圆圈，右侧不显示数量，数量仅出现在各自子任务物品行，下方显示任务名称。当前任务内不再提供“查看浅层地图”“查看芽芽与铁山卡组”按钮。盐池探索子任务仍预留为空，实际地区到达事件尚未接入，不通过界面操作伪造完成。

餐厅左上角在首次成功交单后以图标与数值常驻显示声望和金币。料理交付奖励按星级累计：三星 +100、二星 +80、一星 +60；旧版 10/12/15 凭证只作读档兼容，不重复补发。每份订单另有固定金币配置 `order_gold`（订单金币），取值必须为5–20的整数；盐烤岩鬃肉为5，1/2/3星均获得5金币。类型、前台接单触发和吧台交付完成条件保持不变。配方目录是实际结算来源，任务配置的完成条件登记相同奖励与字段引用；金币、声望、料理消耗、任务归档及结算凭证在同一次原子保存中提交，重复交付零奖励，失败全量回滚，旧已完成档不补发。余额归零仍沿用首单凭证。

2026-10-10后续顾客规则见 `restaurant_customers.md`：首客在真实首访迷宫返回时到店，共三席、四类统一演出；三人的正式配置仍待提供。现有单订单事务不是三客生产流程，需后续实现多订单与座位生命周期。送餐／冷藏当前统一未解锁，正式玩法延后。

老档读取时根据有效首单与准备出发记录补齐任务日志，仅迁移内存，不为读取重写文件。下次业务事务提交时与原业务字段一起原子保存。任务查询不写盘，重播只改独立回放状态，保存失败沿用原有业务全量回滚。未识别的新版本任务实例仍保留在存档中，旧客户端暂不显示。
