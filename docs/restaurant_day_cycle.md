# 餐厅五分钟营业循环（REST-04）

2026-11-04：本规则替代旧六席自动入座、20秒饮水、60秒料理规则。当前改动先在独立工作树验收，目标游戏工作区的集成由主会话负责；独立验收不能代替目标集成。

## 玩家流程

第一章及章末完成后，通过原营业牌和菜单确认开业。菜单最多五道、每道1—10份，开业时先绑定已有同菜成品、锅中料理及完整手持原料，其余份额预留仓库原料，不立即扣料。玩家仍逐单在仓库选择完整配方取出。原地图尺寸、其他道具、铁山剧情及首单保持独立。

餐厅保留原三座和独立前台。新客间隔12秒；三座全占用或前台已有客人时不再生成。新客在点餐处渐显，玩家近距离按E接单后，前台渐隐、座位渐显，不走前台到座位的路径。前台最多一位；没有自动接单。营业计划按来客累计配额约30%先点甘露水，其余直接点料理，复用原三位冒险者素材。每十份计划恰好三位先点水，小样本按整数近似。

新日菜单份额只有售出或实物损耗才消耗。候客、等水、等餐超时释放未消耗额度，随后可补客；订单只占用额度。售出加损耗达到菜单总份数、且所有顾客离场后自动结算。营业牌“结束”按钮复用共用二次确认窗；确认期间暂停营业计时并锁输入，取消恢复，保存失败留窗重试。主动结束无罚关闭未完成订单。营业300秒到时优先无罚无奖结束所有未完成订单，停止耐心、来客和服务，立即显示“结算中”并弹窗，不等顾客走完；背景顾客在原地渐隐离场。同帧耐心归零也不扣罚。主动结束、全部份额完成、300秒到三条路径共用一次持久结算。确认保存成功后进入下一天准备，清理未离完旧客；保存失败保留弹窗重试。菜单按钮仅准备阶段显示，首次探索门槛不变。

## 耐心、交付与反馈

| 情况 | 计时或奖惩 | 后续 |
| --- | --- | --- |
| 前台候客 | 到达点餐处开始40秒；超时金币−1、声望−1 | “怎么没人招呼……”失落、线团，然后离场 |
| 等水 | 坐稳开始40秒；超时金币−2、声望−1 | “水还没好吗……”不耐烦、线团，然后离场 |
| 等料理 | 坐稳或送水成功后开始100秒；超时金币−2、声望−1 | “等太久了！”生气、怒筋，然后离场 |
| 错误料理 | 消耗料理、金币−2，不扣声望；等水时送料理也视为错菜 | “这不是我点的！”生气、怒筋，然后离场 |
| 不达标水 | 消耗水、金币−1，不扣声望 | “这杯水不太对……”不耐烦、线团，继续100秒等料理 |
| 未点水上水 | 消耗水、无奖惩，不重置料理剩余时间 | “咦，我没点水呀？”疑惑、问号，继续等料理 |
| 正确服务 | 料理沿用目录售价及星级声望；达标水7金币 | 水后点料理；料理后进食，再离场 |

前台或座位渐显完成前不消耗耐心。最后20%剩余耐心才显示气泡红色预警；主体与尖角共用连续轮廓。候客文案为“…”；普通上菜仅显示选中顾客头顶E，吧台不另显示通用上菜矩形按钮。取料、倒水、冰镇、烹饪仍计时；首章、剧情暂停、离线及离开餐厅不推进普通营业。普通料理交付按靠近的座位选中目标，不能自动找匹配顾客。前台与其他道具继续使用原距离显隐和输入锁。餐厅普通短暂提示固定在距顶部100像素处，避免遮营业牌及日数；新客和接单成功不重复提示，交付保留账务反馈。迷宫提示位置不变。

反馈复用 `customer_feedback.gd`（顾客反馈组件）、原眉嘴透明层和头发动效，显示2.2秒；文字避开屏幕边缘及营业牌。反馈时保留原瞳孔，隐藏订单气泡；不离场的水反馈结束后恢复订单气泡。普通顾客正常用餐结束后在座位处切回站姿，原地渐隐0.35秒，保存离场成功后移除人物、释放座位；读档从原座位恢复淡出，保存失败保留订单重试，不重复奖励。2026-11-05统一修正：候客超时、等水/等餐超时、错菜、主动结束、时间到及旧档顾客全部共用原地站起并渐隐0.35秒；异常反馈仍先显示2.2秒。离场保存失败时保持透明，只重试保存，不重新显现或重复反馈。进食被打烊中断后，旧进食回调停止，不干扰离场。接单仍为前台原地渐隐、座位原地渐显，铁山首章使用独立流程。

甘露水保留本次快照的杯子和冰度规则：3秒达到加冰，累计超过8秒损坏，取出暂停累计，重新放回不重置进度。倒量和冰度任何一项不达标均按不达标水处理；损坏水也继续料理。空杯不能交付。食材、料理、水仍沿用单类手持约束。

## 存档与事务

普通订单 `cycle`（营业订单标记）沿用原ID；`stage`（需求阶段）包括 `front`（候客）及 `drink/food/done`（等水/等料理/结束）。`phase`（演出阶段）的 `arriving` 表示前台渐显，`seating` 表示前台渐隐及座位渐显。金币、声望最低为零；扣罚、物品消耗、订单变化和凭证同次保存，失败回滚。已经进入离场阶段的失败不再扣罚，读档继续演出。

`restaurant_day_v1.settlement`（待确认营业结算）冻结本日统计；`closing` 状态仅表示结算中，不允许继续服务。开业保存日初金币、声望和服务序号。结算展示本日完成料理单、订单收入/扣款、净金币变化和声望变化；收入包含送水回执。新回执记录余额下限后的实际变化。旧营业档无起点时，以当前序号减本日已来客数限定回执范围并明确标注，仅展示可证明的本日回执；旧回执缺实际差额时展示其记录额。不得把全部历史累计当成本日收入。确认不发钱，只跨天；失败全量回滚。若修改订单编号、奖励来源或存档结构，应重新审查该统计边界。

2026-11-05第十一版接入：结算界面左金币与右图表读取本日 `income`（营业收入），声望读取本日实际变化，扣款/净变化/料理完成单数放在左面板悬停说明。`history`（每日结算历史）随结算原子保存、按日去重，只保留含当前日最近六个日历日的可确认凭证。旧档只采用已有 `last_settlement` 和当前结算，不用累计余额推算历史；一天只有节点，缺失日期不补零、不连跨缺口的线。

`portions_revision=1`（逐份归属版本）及 `portions`（菜单份额）记录每份料理的来源：仓库预留、手持原料、锅中、手持成品或冷藏成品；终态为售出或损耗。订单的 `portion_id`（份额编号）只占用额度，超时释放。正确交付消耗当前订单份额；同菜乱序交付交换实物来源，保留另一订单。点A交B只消耗B实物及可用B额度，A可补客；菜单外B不减A额度。

打烊将所有剩余菜单份额记入损耗，按来源一次性扣除对应仓库原料、手持原料、锅或具体成品；锅中原料已经扣过，不再次扣仓库。额外同菜及菜单外库存保留。`dish_losses`（本日真实料理损耗）包含误送、主动丢弃和打烊剩余份额，实物损耗只记一次。结算新增 `menu_sold/menu_lost`（菜单售出/损耗份数），两者之和等于菜单总份数；来源与库存不符时整次拒绝，保存失败全量回滚。

旧营业没有逐份来源证据时仅结算可确认账目，不猜测追扣原料或成品；结算明确提示旧存档缺少完整损耗记录。确认跨天后下一日使用新账。新账三评价分别是“今天的料理全部售出，一点也没浪费！”、“今天的料理都损耗了，下次留意接单和上菜时间吧！”、“今天有部分料理损耗了，下次合理安排备餐与上菜吧！”。新增库存入口、料理销毁、配方共享原料或存档迁移时须重新检查来源守恒与事务回滚。

六座旧档采用 `layout_revision=3`（三座布局修订）一次性映射：前三个已接单顾客映射三座，多余最多三位保存在 `legacy_waiting`（旧档已接单待入座记录）。订单ID、阶段、剩余时间、结算记录保持；待入座时暂停耐心，腾座后优先恢复，走到座位才继续原阶段。该记录只用于旧档兼容，不生成新的普通候客队列。未接单客不会被迁移提前接单。映射读取不写盘，由服务原子保存，失败保留原始档。

第一章继续使用铁山独立事务、对白和原料理气泡。`chapter_layout.gd`（章节布局）恢复原吧台交互轮廓，坐标使用显式二维向量；标量数组构造会得到零向量，不能用于运行时轮廓。

## 验收入口与边界

`tools/tests/restaurant_rest04.tscn` 为结算专项，默认覆盖事务、双尺寸实际场景及铁山回归，`-Mode resume` 检查渐变及结算读档实际场景。通过 `tools/tests/restaurant_service_cycle_run.ps1 -Scene res://tools/tests/restaurant_rest04.tscn -OutputRoot <新输出目录>` 启动隔离存档。`restaurant_three_seat.tscn` 保留三座、旧档迁移、反馈与完整服务回归，其结算断言已按REST-04更新；`-Mode service` 验证实际菜单、E接单、倒水冰镇、取料烹饪、交付和确认结算；`-Mode clock` 验证墙钟；`-Mode migration` 验证旧六座迁移；`-Mode feedback` 验证反馈路径。

历史 `restaurant_service_cycle.tscn` 包含旧冰度与六座假设，仅复用其中适用的验收辅助方法，不将旧断言结果作为本票依据。实际命令、结果、截图和限制登记在本票交付记录。任何布局、人物素材、冰度评分、耐心或存档结构改变时，重新运行受影响专项及首章回归。
