# 迷宫场景制作路线：从分水庭复用到下一场景

整理日期：2026-11-07。本文汇总用户在分水庭制作中已经确认的方式，供下一场景沿用；不是新授权，不替代当前用户决定、项目 AGENTS.md 或票据细则。

核心路线：文档与实装盘点 → 整图体验对齐 → 布局及视觉预览 → 规格与纵向拆票 → 素材制作及程序接入 → 真实战斗验收 → 统一网页试玩 → 根据反馈迭代。

## 一、按什么顺序制作

| 阶段 | 具体工作与产出 | 进入下一阶段的依据 |
| --- | --- | --- |
| 1. 盘点文档与实装 | 对照飞书、项目文档和实际地图，列出地形、怪物、资源、宝箱、剧情、出入口及现有行为；区分已有、缺失和历史失效描述 | 明确本次场景、范围、实际运行入口和需要保留的内容 |
| 2. 对齐整张地图体验 | 先定玩家在这里做什么、地形如何影响战斗、普通怪能否绕过、资源附近如何读懂风险、是否有可选小高潮，以及剧情如何不被干扰 | 用户认可整图体验及关键规则；不是先孤立打磨一只怪物 |
| 3. 评审布局与视觉 | 用现图标注遭遇区、引怪与绕行路线、可走面、预警和伤害范围；列出方向、动作、特效及挂点缺口，提供预览 | 用户确认布局和需要制作的视觉方案；草图不等于可走验证 |
| 4. 固定规格并拆票 | 写明问题、方案、玩家操作、实现与测试决定、排除项；按一个可独立试玩的完整行为拆票，注明依赖、文件归属、预算和验收 | 用户确认规格及票据边界；只启动输入已齐的票据 |
| 5. 制作素材并接入 | 视觉会话按已认可提示词绘制、改稿；游戏会话接收结果，处理切图、方向、透明、锚点、层级、尺寸与真实技能时序 | 素材有对应确认记录，实际游戏消费的是本次交付，不以动作播放器代替战斗 |
| 6. 在真实游戏验收 | 从真实输入验证攻击、锁定、受击、范围、同场多怪与多种效果叠加，以及直接相关的失败和恢复行为 | 游戏会话完成自检，来源主会话亲自完成约定验收；计数通过不代替看实际画面 |
| 7. 交付统一网页试玩 | 在主区增量整合，重新导出网页，核对服务目录、构建版本、端口及实际画面，再交用户体验 | 地址确实服务本次构建；源码已改不等于网页已更新 |
| 8. 按试玩反馈迭代 | 先确认用户所玩版本并复现；区分视觉问题、程序接入、参数及旧包，按影响范围修正、复验并回传对应会话 | 保留通过项与原始失败证据；需要新外观或扩大范围时先对齐，不无界续修 |

阶段会按依赖交错推进：确认过的素材可以制作，已具备输入的完整行为可以接入；不要求整张地图先写完全部逻辑再补视觉，也不能在视觉未确认时直接发布。

## 二、先问清哪些设计问题

下一场景先围绕这些对象对齐，不默认继承分水庭的具体答案：

- **整图目标**：轻巧冒险还是高压战斗；从入口到出口的主要路径、可绕路线与可选挑战。
- **地形玩法**：该地形带来什么优势、风险及玩家可利用的办法；哪些行为只在本图启用。
- **普通遭遇**：怪物如何发现、追击、出招、回位；资源附近如何预先观察并避险。
- **小高潮**：如有精英怪，玩家应观察什么、何时反击、失败后如何重新尝试。
- **反馈可读性**：蓄力、预警、有效范围、命中、保护、硬直和恢复，玩家分别能看到什么。
- **内容保护**：剧情、宝箱、采集及必经路线是否会被战斗影响，离图与读档如何恢复。

分水庭采用的水中保护、引怪上岸、借电和巨蛙最高点反击，是地形相关的实例，不是每张地图都要复制的模板。

## 三、会话职责与确认点

| 责任方 | 负责 | 不自动承担 |
| --- | --- | --- |
| 用户 | 整图体验、关键规则、布局及视觉方案确认，试玩反馈 | 不需要手工搬运会话间交付或反复确认同一已授权事项 |
| 场景统筹／游戏接入会话 | 文档和代码盘点、方案对齐、规格与票据、共用模块接入、真实战斗验收、网页交付及回传 | 不自行替用户与视觉会话确定提示词，不擅自生图或改已认可造型 |
| 视觉会话 | 与用户对齐完整提示词、风格、预览、改稿及素材交付 | 不把素材预览当作游戏接入完成；工具开发归属以原票为准 |
| 原编辑器会话 | 编辑器工具、实际参数消费者、保存及历史恢复；说明草稿、训练场和正式游戏生效边界 | 新场景会话不重复开发编辑器，不默认恢复其旧预算或发布候选服务 |

下一场景若需要新的视觉执行会话，先在该场景的已确认范围内明确归属；本次新建的只是场景准备与对齐会话，不连带创建其他任务。

历史采用过 grill-with-docs（基于文档追问对齐）→ to-spec（整理规格）→ to-tickets（拆票）→ implement-spec（按规格实施）。后续仅在对应技能实际可用并完整读取后使用；不可用时明确说明，按项目要求的同等字段整理，不假称运行，也不自行安装。

## 四、素材怎样交付才方便接入

1. 生成本项目图片前，读取对应飞书章节，把图片风格提示词原文纳入实际完整提示词，注明来源；不能仅写“水彩风”。首次提示词及视觉预览由用户确认，已确认范围内的改稿和交接不重复索取相同批准。
2. 交付时给出实际文件、采用版本、透明／切图情况、帧序及节奏、对应朝向、挂点、标定尺寸、播放时段与已知缺口。未确认项保留为候选。
3. 命中特效按同一招式的既有标定显示，不跟受击怪物体型一起放大。落地水花等与施法者体积相关的效果，则按该素材已确认的比例接入；两者不能混用一套缩放规则。
4. 接入后同时核对实际接触点、腾空高度、遮挡、四向人物受击、动作持续时间，以及多种效果同时出现的画面。不能仅凭透明图或单帧预览判定合格。
5. 范围攻击统一核对预警、落地／放电效果和伤害结算在地图中的同一范围；如有视觉消散的装饰部分，边界先对齐，不让玩家靠猜测避伤。

## 五、复用已有战斗模块，不在每图复制

- 角色模块：PlayerCombatController（角色战斗控制器）负责安装与输入、锁定和切换；PlayerCombatRules（角色战斗适用规则）确定正常地图适用性。入口见 [角色模块说明](player_combat_controller.md)。
- 怪物模块：MonsterCombat（怪物共用战斗状态与结算）集中基础属性、共同可攻击资格和命中处理；各怪追击、冲刺、放电、跳跃及地形策略留在原专属实现。入口见 [怪物模块说明](monster_combat.md)。
- CaptureRun（探索事务）仍管理生命、经验、捕获和保存；显示层不另造扣血、死亡或存档状态。锁定、卡肉和受击使用现有链路，不因新场景再建副本。
- 下一场景只补它的地形、怪物和招式差异。需要改变共用接口时先核调用方、编辑器依赖及相关测试，再增量修改，不为推测性未来需求扩大抽象。

## 六、验收与试玩的固定关注点

- 正常：真实出招和扣血、同招式命中尺寸、卡肉与击退、锁定／切换／解除、受击时不能继续走攻、方向与遮挡、范围内外及多怪同时交互。
- 相关错误和恢复：打空／无效目标／失败保存不泄漏事件；连续受击、暂停恢复、离图、死亡、捕获和读档不留下卡死输入或过期锁定。具体项目随票据风险确定，不做无关穷举。
- 视觉：真实连续播放与关键帧都要看；单独列出仍未确认的外观，不能把程序测试通过写成用户终审通过。
- 输入：测试只用 Godot 内部模拟事件或专用无界面浏览器，不接管用户的系统鼠标键盘。需要窗口时沿用已授权的不可聚焦安排；锁屏网页测试先读对应细则。
- 节奏：优先复用现有入口与已验证证据，只补变化或缺失部分；修复期间聚焦复测，收尾完成本票约定的最终检查。发现同链问题集中列清，不反复从头准备。
- 版本：交付明确主区、实际构建、访问地址和限制；核实浏览器真的载入新版。参数保存、训练场预览、源码读取和网页重导出是不同环节，不能互相替代。
