# 料理迷宫：开发准备与 Agent 协作指南

本项目使用 Godot 制作手绘二维餐厅与迷宫探索游戏。本指南帮助团队成员准备环境、初始化自己的 Agent（开发助手），并完成需求沟通、实现、调试、验收和版本交付。

协作规则以 [AGENTS.md](AGENTS.md) 为准，玩法设计看 [游戏大纲](docs/game_outline.md)，实际入口和实现以当前分支的配置、代码为准。本页提供操作步骤和对话模板；示例中的地图名、范围、路径和验收条件需要换成本次任务的实际内容。

## 1. 第一次开发前准备什么

### 环境与路径

| 准备项 | 用途与检查方法 |
| --- | --- |
| Git、仓库访问权限 | 克隆、创建分支、提交和推送；运行 `git --version` |
| Git LFS（大文件存储） | 拉取序章视频；运行 `git lfs version` |
| Godot 编辑器 | `project.godot` 声明 4.7；本指南核对时原开发机为 `4.7.2.stable.steam`，先与团队对齐版本，再运行 `--version` 核验 |
| PowerShell 7 | 运行 Windows 开发与验收脚本；运行 `pwsh --version`。部分脚本使用新版 .NET 接口，不能假设系统自带的 Windows PowerShell 5.1 可直接执行 |
| 可访问本地仓库的 Agent | 能读取文件、查看 Git 差异、执行命令；图形界面操作和生图能力按任务需要配置 |
| 按需安装的素材工具 | 仅在对应脚本要求时安装 Python、图像处理库、Blender 等，不是启动游戏的统一前置条件 |

原开发机使用 `F:\maze_code`，引擎位于 `F:\SteamLibrary\steamapps\common\Godot Engine\godot.windows.opt.tools.64.exe`，工作树优先放在 `E:\codexWorktree`。这些是机器路径，不要求团队成员使用相同盘符。首次对话明确自己的仓库、引擎和工作树路径，运行旧脚本时显式传参覆盖默认路径。

### 获取代码与大文件

以下在 PowerShell 中执行，先把路径换成自己的位置。`codex/region-1-maps-20261027` 是本次第一区域版本的交接分支，后续应由负责人指定开发基线，不将它永久当作“最新版本”。已有工作区先检查未提交改动，不直接覆盖或切换正在开发的内容。

```powershell
git lfs install
git clone --branch codex/region-1-maps-20261027 https://github.com/wendyluk-code/maze_code.git D:/work/maze_code
Set-Location D:/work/maze_code
git config core.longpaths true
git lfs pull
git lfs ls-files
git status --short --branch
git rev-parse HEAD
```

确认 `assets/video/prologue/prologue_opening_zh.ogv` 已取得真实视频，而不是只有几行文字的 LFS 指针文件。拉取失败时先解决仓库访问或 LFS 错误，避免把资源缺失误诊为游戏代码问题。

本地 `tools/godot_portable/` 的编辑器、导出模板和缓存未随本次版本上传，需要自行安装引擎。导出安装包才需要匹配版本的导出模板；日常从编辑器运行不依赖这份本地目录。

### 首次启动

在仓库根目录打开 PowerShell 7，设置本终端使用的路径：

```powershell
$projectRoot = (Get-Location).Path
$godotExe = 'D:/tools/Godot/godot.windows.opt.tools.64.exe' # 替换为实际路径
if (!(Test-Path -LiteralPath $godotExe)) { throw '请先填写正确的 Godot 路径' }
& $godotExe --version
& $godotExe --editor --path $projectRoot
```

也可以在 Godot 项目管理器导入仓库根目录的 `project.godot`。等待资源导入完成，再运行整个项目。首次验收应看到开始界面，能够进入新游戏或读取测试存档，并按剧情进入餐厅。移动使用 WASD / 方向键，交互使用 E；具体场景的按键以画面提示和当前输入配置为准。

当前启动入口为 `scenes/start_screen.tscn`，餐厅主要场景为 `scenes/restaurant_map_2d.tscn`。直接启动餐厅或迷宫场景可能缺少前置状态，不能用它代替完整入口验收。`scenes/restaurant_2d.tscn`、`scenes/restaurant.tscn`、`scenes/village_3d.tscn` 是历史原型入口。

首次准备完成的标志：已记录引擎版本、分支和提交，资源导入无阻断错误，能从开始界面进入游戏；启动后的新增文件和改动已经核对。

### 可选：连接 Godot 编辑器

仓库已配置 `addons/godot_ai/` 插件及 `_mcp_game_helper` 自动加载节点。需要 Agent 直接检查编辑器场景、运行游戏或获取调试信息时，阅读 [插件说明](addons/godot_ai/README.md)，按该插件流程安装 `uv`、启用插件并配置自己的客户端。MCP（模型上下文协议）是 Agent 与编辑器工具通信的接口。

配置后让 Agent 实际读取一次当前场景，验证连接可用。没有连接能力时，仍可使用终端、Godot 编辑器和人工截图配合开发；缺少图形操作能力应明确披露。插件目录默认不属于游戏功能修改范围。

## 2. 给自己的 Agent 做初始化

先在 Agent 中打开自己的仓库目录，将下面模板中的尖括号内容填好后发送。它分成两步，避免把“了解项目”误当作实现授权。

**第一条：说明环境和本次初始化目标。**

```text
我们要在这个仓库协作开发《料理迷宫》，默认用中文交流。
我的仓库路径：<绝对路径>
Godot 可执行文件：<绝对路径>
工作树根目录：<本机短路径>
本次集成与验收的目标工作区：<绝对路径>

这次只做开发初始化：核对环境、当前分支、项目入口和协作规范，
输出初始化检查结果及阻断项。不要修改游戏代码、切换分支或推送。
先复述目标、范围、交付物和验收标准，等我确认后再开始盘点。
```

**Agent 复述准确后，再发送：**

```text
确认上述初始化范围。请读取根目录 README.md、AGENTS.md、
docs/game_outline.md、project.godot，并检查当前目录适用的补充指令。
运行 git status --short --branch、git rev-parse HEAD，识别并保护已有改动。
核对实际 Godot 版本、主场景、自动加载单例和可用测试入口。
列出你实际读到的规范路径、可用工具及仓库内 Skill；缺失能力如实说明。

AGENTS.md 中原开发机的绝对路径按我提供的本机路径使用。
发现历史状态与当前代码不一致时，报告依据，不擅自改写规范或扩展任务。
交付：环境是否就绪、当前基线、已有改动、可运行的启动/验收命令、待解决项。
```

Codex 会读取适用的 `AGENTS.md`；仍应要求它列出实际读取来源，确认打开的是正确仓库。使用其他 Agent 时，显式让它读取该文件及本次相关 Skill，不假设不同产品会自动加载相同文件。[官方说明：AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

### Skill 是否随仓库共享

Skill（技能）是针对特定任务的操作说明和参考资料。本仓库已共享 [new-map-development](.agents/skills/new-map-development/SKILL.md)，包括需求收集表、实现定位与验收参考，可用于新地图、区域怪物和地图换图任务。

Codex 支持从仓库 `.agents/skills/` 发现技能。若当前客户端未显示该技能，可先让 Agent 直接读取上述 `SKILL.md` 及其引用文件，并检查工作目录和客户端技能配置。[官方说明：本地技能](https://learn.chatgpt.com/docs/build-skills)

原开发者个人目录中的技能、插件、账号配置和对话历史不会因克隆仓库自动共享。例如个人使用的 `restaurant-order` 技能不在当前仓库技能目录中；团队若需要，应另行安排共享，不能让 Agent 假装已经读取。没有技能时先说明缺口，在已确认范围内依据项目文档工作。

## 3. 日常如何与 Agent 对话

日常节奏是：**说清玩家行为 → Agent 复述并提问 → 确认范围 → 实现和验证 → 人工试玩反馈 → 修正复验 → 交付版本。** 开发者决定玩法、素材选择和验收结果；Agent 负责查代码、定位接入点、实现以及提供验证证据。

### 提出一个开发需求

先描述玩家能做什么、现在有什么问题、期望什么变化；不必替 Agent 猜脚本名。下面是格式示例，不代表已经批准这些功能：

```text
我要做：<例如新增一张与分水庭连接的地图>
玩家流程：<从哪个入口进入，在图里做什么，如何返回>
已有素材：<附件/仓库路径；说明哪些是参考图，哪些是正式素材>
要保留：<现有交互、存档兼容、地图入口、他人改动等>
本次不做：<例如新剧情、新料理、新怪物>
验收：<进入/取消、移动与阻挡、返回、退出重进、指定分辨率截图>
请先复述目标、范围和交付物，列出会影响结果的缺失信息，等我确认。
```

新地图可直接说：

```text
使用 $new-map-development，为<地图名>整理开工前的确认事项和素材清单。
先只整理需求，不实现。参考分水庭的<具体特征>，保留<具体规则>。
不要自动扩展餐厅剧情、任务或料理；不确定的玩法请明确问我。
```

Agent 应查明工程路径、区域标识和坐标换算；开发者需要确认地图用途、通路、入口/返回点、怪物行为、奖励及素材来源。“沿用现有”应指出具体对象，不能用这句话跳过差异确认。

### 确认后怎样推进

```text
确认你列出的范围和验收标准，开始执行。
请保留现有用户改动，在已确认范围内完成实现、集成和复验。
同一范围内的常规步骤无需重复问我；新增玩法或扩大范围时先列出变化。
进度说明已发现什么、还缺什么证据；最终给出实际路径、差异和验收结果。
```

小任务可由当前会话完成。复杂任务先形成能独立演示的纵向票据：一张票据贯穿玩家操作、状态、界面和必要存档。例如“进入新图、交互、返回并恢复状态”是一条完整行为；单独“先写数据层、以后再接界面”不能当作可演示交付。

需要新建可见执行任务时，明确说“按这些票据创建独立任务”，并先审阅票据。票据包含编号、行为、允许修改位置、排除项、受保护改动、`Blocked by`（阻塞依赖）、验收、Git 基线与分支、目标工作树、预算和允许提交与否。具体派发、并发、止损和交接协议统一见 [AGENTS.md 第 4—9 节](AGENTS.md)。

### 图片设计与改稿怎样说

首次明确用途、构图、画风、参考图借鉴点、准确文字、尺寸、透明背景和切图要求，让 Agent 展示准备提交的完整提示词。确认提示词后执行；直接提出的改稿要求沿用其余已确认约束。

```text
这张图用于<游戏背景/角色动作/界面>，参考图只借鉴<具体特征>。
尺寸<宽×高>，背景<透明/不透明>，准确文字是<文字或无文字>。
本次交付<仅设计稿 / 设计后切图并接入游戏>。
先给我完整提示词确认，再开始生图。
```

改稿示例：“把右侧植被降低，保留道路和入口位置，其他要求不变。”若只批准设计稿，先交图审阅；切图和接入是否执行，沿用此前明确授权的范围。

### 对话过长、换 Agent 或换开发者

要求原 Agent 留下：已确认目标、明确排除项、当前分支与提交、未提交差异、已做事项、真实测试结果、失败证据、未验证项和下一步。将交接记录交给新 Agent，先核对实际工作区，再继续原范围；已确认内容不因换会话失效。不要仅发送一句“继续做”，也不要把历史通过记录当成本次已经通过。

## 4. 调试的完整流程

### 第一步：给出可复现的问题

```text
在<分支/提交>，使用<新存档/测试存档及所处阶段>。
窗口分辨率：<宽×高>。
复现：1.<进入场景> 2.<按键或点击> 3.<出现问题>。
实际表现：<角色卡住/提示不消失/状态错误等>。
期望表现：<应该发生什么>。
发生频率：<每次/偶发；已尝试几次>。
证据：<截图/录屏/日志路径，标记问题位置或时间>。
请先复述修复范围和验收标准，确认后先复现，再做最小修改并复验。
```

画面问题尽量给全窗口截图和局部标注；状态问题记录操作前后的库存、队伍、任务或存档阶段。报错附完整错误栈及前后日志，不只截最后一行。使用 Godot 编辑器的输出和调试器查看错误；需要核对运行节点时查看运行中的场景树，而不是只看编辑状态。

### 第二步：隔离存档，再运行测试

`user://` 是 Godot 的用户数据目录，不是仓库目录。当前存档实现使用 `user://save.json` 和 `user://saves/`；Windows 默认位置通常为 `%APPDATA%/Godot/app_userdata/maze_code/`，以实际运行的用户数据路径为准。

测试前关闭会写正式存档的其他游戏进程。复现用户存档问题时先备份，并让测试使用副本；新流程使用独立测试存档。切换 Git 分支不会隔离 `user://`，不同工作树也可能访问同一份正式存档。

现有部分 PowerShell 运行器通过子进程的 `APPDATA`、`LOCALAPPDATA` 和测试标记隔离存档，并检查正式存档指纹。运行专项前让 Agent 阅读运行器及其测试脚本，核实环境变量、参数、超时和报告路径。测试场景中的 `_verify_isolation()`（隔离检查）失败时，应修正运行环境后重试，不能删除检查绕过。

### 第三步：用隐藏调试面板准备状态

在编辑器运行或调试构建的游戏窗口内，依次输入 **78789**，相邻数字间隔不超过 3 秒，支持主键区和数字小键盘。可增加金币、星尘、队伍饱腹度，或补满队伍饱腹度；按 Esc 或点击关闭恢复游戏。

**操作会立即写入当前加载的存档**，因此应在测试存档中使用。饱腹度输入是按队伍顺序分配的全队总量，受各角色上限限制。正式发布构建关闭此入口；重播和序章预览拒绝修改。实现和验证边界见 [本地调试工具](docs/local_debug.md)。

调试面板用于准备资源状态；订单、任务完成和奖励发放仍须按本次验收要求经过真实流程验证。

### 第四步：从基础检查到实际场景

以下复用现有运行器，在 PowerShell 7 中执行，沿用前文的 `$projectRoot` 与 `$godotExe`。每次使用新的输出目录，检查命令退出状态和保存的日志。

```powershell
$evidenceRoot = Join-Path $projectRoot ('output/onboarding_' + (Get-Date -Format 'yyyyMMdd_HHmmss'))
& "$projectRoot/tools/tests/ch2_entry_run.ps1" -Mode import -ProjectRoot $projectRoot -Godot $godotExe -OutputRoot "$evidenceRoot/import"
& "$projectRoot/tools/tests/ch2_entry_run.ps1" -Mode smoke -ProjectRoot $projectRoot -Godot $godotExe -OutputRoot "$evidenceRoot/smoke"
```

`import` 检查无界面编辑器导入，`smoke`（冒烟检查）短暂启动主入口。先查看前一条结果，失败时处理后再继续。它们使用隔离配置，只能证明相应检查覆盖的部分；无头模式没有图形画面，不能证明碰撞、镜头和真实输入正确。首次资源导入仍应在编辑器确认完成。

之后按改动选择专项，不默认全跑历史测试：

| 改动 | 应检查的入口与证据 |
| --- | --- |
| 地图通路与碰撞 | `tools/tests/salt_map_connectivity.gd` 等连通检查，以及真实场景移动截图；采样连通不能代替全部岸线和障碍验证 |
| 分水庭与盐池往返 | `tools/tests/salt_pool_flow.tscn` 及其继承脚本；入口确认/取消、切区、地图定位、返回和存档状态 |
| 重启恢复 | `tools/tests/fenshui_restart.tscn` 等独立进程测试；记录两次进程使用同一测试存档，不能只在原进程重载 |
| 隐藏调试面板 | `tools/tests/local_debug.tscn`；按键呼出、实际点击、数值保存、关闭恢复输入 |
| 界面或弹窗 | 受影响场景的显示、距离显隐、确认/取消、关闭后输入恢复；参考既有 1152×648、1280×720 验收尺寸 |

这些是测试定位入口，不是统一启动命令；直接运行测试场景可能缺少隔离环境、报告和截图参数。先由 Agent 核对测试仍适用于当前需求，再给出本次可执行命令。尤其历史地图测试可能保留旧坐标或“无怪物”等旧假设，不能为了让它变绿而回退当前玩法。

### 第五步：解释结果并复验

每次修复按“问题证据 → 根因假设 → 最小单变量实验 → 实际结果 → 结论边界”报告。若仍复现，反馈相同步骤和新证据，让 Agent 在原范围继续定位；出现新问题类型或需要扩大范围时重新确认。

最终在目标工作区运行真实场景，保留启动命令、引擎版本、分支/提交、退出码、日志、报告和截图。检查报告中的失败数、截图对应行为和存档隔离，不能只看进程返回 0。涉及持久化时还需退出进程后重进验证。

`output/` 已被 Git 忽略，可存本次证据；交接时另行提供可访问的证据位置，仓库文档中指向原开发机 `output/` 的路径不意味着团队能直接取得截图。系统证书或沙箱日志权限错误单独披露；脚本解析、资源缺失和场景运行错误必须处理，不能混作环境噪声。

## 5. 团队并行开发与交付

每位开发者使用独立工作区或 Worktree（Git 工作树，即同一仓库的独立检出目录），每个写入票据独占分支和文件范围。主会话是负责协调和集成的 Agent 会话，执行任务是在票据范围内工作的独立会话。单写者租约表示某些文件在该任务期间只有一个写入者；交付前须明确停止写入并释放所有权。

基线 `base_ref` 是可读分支/标签，`base_commit` 是对应的固定提交，`ticket_branch` 是本票据分支。`HEAD` 表示当前检出的提交。派单前记录这些值和用户改动；执行任务核对基线、目录及分支后才动工。只启动依赖已完成的票据。

Codex 可见任务遵循 [AGENTS.md 的派发协议](AGENTS.md)。其他 Agent 若没有独立任务、消息或等待工具，应报告能力缺口，由开发者明确单任务或人工交接方式；不能声称已创建、已通知或会自动继续。

执行任务完成后停止写入，提交结构化交付给主会话。主会话审查差异，保留目标工作区的用户改动，按依赖增量合入，再在目标工作区做集成验收。只在独立分支通过、尚未合入，仍属于中间状态。

新增界面先读 [UI 组件库](docs/ui_component_library.md) 及组件实现；新增或改型游戏任务先读 [任务规范](docs/quests.md)，确认类型、触发和完成条件，按需同步任务目录及迁移。修改 `SaveManager`、`TutorialManager` 等 Autoload（自动加载单例）接口前检查所有调用方。

### 交付时让 Agent 回答什么

```text
请按已确认范围交付：
1. 已完成或未完成，实际目标工作区和分支、提交。
2. 修改文件、玩家行为变化，以及保留的已有改动。
3. 实际执行的命令、场景操作、测试结果、截图和日志位置。
4. 哪些没有验证、原因是什么、恢复条件是什么。
5. 若使用执行任务，是否停止写入、已交接且已合入目标工作区。
6. 可复用的已验证结论及何时需要重新检查。
```

“实现完成”“已验收”“已提交”“已推送”分别报告。未达到本次验收标准时写“未完成”；局部通过或候选修复不能代替全流程交付。

### 提交并上传版本

需要上传时明确给出仓库、目标新分支、提交说明和包含范围。例如：

```text
把本次已验收改动提交并上传到 https://github.com/wendyluk-code/maze_code.git。
新建分支 codex/<本次功能名>，提交说明为“<版本说明>”。
先核对差异，包含<已确认文件范围>，保留其他未提交改动。
不要上传本地引擎、缓存、测试存档和临时输出。
上传后核验远端提交与本地一致，并给我分支链接和提交哈希。
```

Agent 应先检查 `git status --short --branch`、差异和远端配置，再暂存本次范围。不要把“当前目录有改动”当作全部应提交的理由。当前本地 `tools/godot_portable/` 未被忽略，整体暂存前特别检查；Godot 的 `.godot/` 导入缓存与项目已跟踪的 `.import` 资源描述文件也需要区分，不能一概删除。

推送成功后用 `git ls-remote --heads origin <分支名>` 与本地提交核对。上传新分支不代表合入团队主分支、发布游戏或创建安装包，这些交付应有各自明确范围。

## 6. 常见情况与后续阅读

| 情况 | 下一步 |
| --- | --- |
| Agent 不知道之前的约定 | 让它列出实际读取的规范和交接记录，核对项目目录；不依赖原开发者个人聊天历史 |
| 资源缺失、序章无法播放 | 检查 LFS 下载、资源实际文件和导入日志 |
| 测试路径指向原开发机 | 显式传入 `-ProjectRoot`、`-Godot`、`-OutputRoot`，核对脚本是否还有硬编码路径 |
| 测试提示正式存档变化 | 检查外部游戏是否仍在运行及隔离路径，保存证据后复验，不忽略指纹检查 |
| Agent 说无头启动通过，但画面仍错误 | 回到真实场景复现、输入操作和截图验收 |
| 上传失败但本地已提交 | 保留提交，记录失败原因，解决权限、网络或大文件问题后上传；不能宣称上传成功 |
| 旧文档与实现不一致 | 区分历史事实与现行规则，按代码核实；玩法范围由开发者确认 |
